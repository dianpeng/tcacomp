# Layout Optimization

# GMEM optimization

- Goal
  - Optimizing the global memory access for global memory coalescence

- Problem Formulation
  - For a GMEM access nodes, regardless load/store
  - A Layout of GMEM is a functional mapping
    - Maps a natural coordinate into a codomain D
      - Effectively perform stride transformation on in put I, which is a N dimensional coordinate
  - The coordinate of GMEM is a parametrized by induction variable
    - c0 * i + b0
    - definition
      - the memory access is within a N dimensional space
      - each dimension is parametrized with a induction variable linked to **thread index**
      - t[0]/t[1]/..t[n-1]
        - notes some dimension in practise may not have induction variable, ie degree of freedom, ignore them
      - each subscript is denoted as transformation ONLY for its given thread index
        - affine transformation
        - denoted as idx(i), 0 <= i < N
    - the optimization becomes
      - for t{i: 0 <= i < N} in its feasiable area
        - constrainted by tiling and warp thread total
      - changing affine transformation theta 
        - s.t all coordinates elements coord(k) (idx(0), idx(1), ...) in feasiable area
        - maximize SUM: theta(coord(k)) * sizeof(dtype) / 128

    - in short
      - ensure that for a batched access in a WARP, ie thread index obtain value (0, 32) s.t all final offset to have most fall in the same 128 bytes range
        - which maiximize the total GMEM coalescense

- Strategy
  - 1) find a transformation trans s.t. the theta.new = theta.old * trans to optimize the object
    - NP-hard
    - Too expensive for us
  - 2) heuristic method: rearrange the polytope by axis permutation
    - notes this is bijective guaranteed
      - the transformation only changes the axis of visiting of polytope's points, not change the points

    - [1] for each idx(i), obtain its slop(i) 
    - [2] obtain its corresponding dimension's extent ext(i) in original shape
    - [3] obtain its stride(i) = slop(i) * ext(i)
    - [4] obtain corresponding induction variable bounds(i)
      - ie bounds of feasiable area
    - [5] obtain the exstimate hit: hit(i) = min(bounds(i), 128 / (stride(i) * sizeof(dtype)))
    - [6] order the rank against its hit(i) ascendingly
      - for dimension that has no degree of freedom, give them smallest hit count as 0
    - [7] derive a permutation vector, based on the ranked order
    - [8] apply such access permutation for all memory access for a operation node
      - WHY? for example, IR nodes access a GMEM for a purpose, ie transfer it into SMEM
        - MemLoad
        - MemStore
        - MemInit: irrlevant
      - Assuming MemLoad, which means load a memory from somwhere from SMEM to GMEM
      - The permutation is in shape/coordinate space, hence it must be carried to the SMEM also
        - notes it permutes the shape, only operate on the dimension axis's order
      - Otherwise data is corrupted !!
  - Conclusion: choose (2) !!!

# 2D Tensor SMEM Swizzle Optimization Design
## Comprehensive Analysis by Induction Variable Configuration

---

## Executive Summary

This design addresses three fundamental 2D tensor access patterns in SMEM optimization, each with distinct bank conflict characteristics and optimal swizzle strategies:

| **Case** | **Shape** | **Induction Variables** | **Conflict Dimension** | **Optimal Strategy** | **Complexity** |
|----------|-----------|------------------------|----------------------|----------------------|----------------|
| **Case 1** | M × N | M varies, N constant | Row-wise | 1D pattern (row-skew) | Low |
| **Case 2** | M × N | M constant, N varies | Column-wise | 1D pattern (col-skew) | Low |
| **Case 3** | M × N | Both vary | 2D interleaved | 2D patterns (multi-D XOR/transpose) | High |

All analysis assumes: compile-time constant M and N (typically power-of-2), 32 SMEM banks, 4 bytes/element.

## Case 1: M Varying, N Constant (Row-Wise Conflict)

### Physical Interpretation

```
Thread layout:        Memory access pattern (M-indexed variation):
┌─┬─┬─┬─┐            Row 0: [T0  T1  T2  T3]  ← All threads same column
│0│1│2│3│            Row 1: [T4  T5  T6  T7]  ← Same column, next row
├─┼─┼─┼─┤            Row 2: [T8  T9  T10 T11] ← ...
│4│5│6│7│
├─┼─┼─┼─┤            Memory addresses (element size = 4 bytes):
│8│9│10│11          A[0][c] → offset = 0*stride + c*4
└─┴─┴─┴─┘            A[1][c] → offset = 1*stride + c*4
  (warps)            A[2][c] → offset = 2*stride + c*4
```

**Key Insight:** All threads in a warp access columns, but from different rows.

### Bank Assignment Analysis

**Without optimization:**
```
Standard layout: stride = N (natural row-major)
  offset(m, n) = m * N * 4 + n * 4
  bank(m, n)   = (m * N * 4 + n * 4) / 4 % 32
               = (m * N + n) % 32

Example: M=16, N=8, thread t accesses A[t/8][t%8]
  Thread 0: bank = (0*8 + 0) % 32 = 0
  Thread 1: bank = (0*8 + 1) % 32 = 1
  ...
  Thread 8: bank = (1*8 + 0) % 32 = 8
  Thread 16: bank = (2*8 + 0) % 32 = 16
  Thread 24: bank = (3*8 + 0) % 32 = 24
  → Conflict-free! (stride N=8, only 8 threads)
```

**Conflict case:** When stride = N and M is large relative to bank count:
```
M=64, N=4:
  Thread 0:  bank = (0*4 + 0) % 32 = 0
  Thread 1:  bank = (0*4 + 1) % 32 = 1
  ...
  Thread 8:  bank = (2*4 + 0) % 32 = (8) % 32 = 8
  Thread 16: bank = (4*4 + 0) % 32 = (16) % 32 = 16
  Thread 24: bank = (6*4 + 0) % 32 = (24) % 32 = 24
  Thread 32: bank = (8*4 + 0) % 32 = (32) % 32 = 0  ← COLLISION with thread 0!
```

### Optimal Swizzle Patterns

#### Pattern 1a: Row-Skew (Recommended for N < 32)

**Transformation:**
```
offset'(m, n) = m * (N + SKIP) * 4 + n * 4

where SKIP is chosen to decorrelate (m*N) term modulo 32.
Typical choice: SKIP = ceil(32 / gcd(N, 32))
```

**Derivation:**
```
Original bank formula: bank = (m*N + n) % 32

With skew stride = N + SKIP:
bank' = (m*(N + SKIP) + n) % 32

For consecutive m values (m, m+1, m+2, ...):
  m:   bank = (m*N + m*SKIP + n) % 32
  m+1: bank = ((m+1)*N + (m+1)*SKIP + n) % 32
             = (m*N + m*SKIP + N + SKIP + n) % 32

If SKIP is coprime to 32, then (m*SKIP) mod 32 creates a permutation
across m iterations, decorrelating rows.
```

**Formula Selection:**
```
if N % 2 == 0:
  SKIP = 32 / gcd(N, 32)
else:
  SKIP = 32  # Force large skip for odd N

Practical heuristic:
  SKIP = 8 for N ∈ {2, 4, 8}
  SKIP = 1 for N ∈ {16, 32}
  SKIP = 16 for N = 1, 3, 5, ... (odd)
```

**Example (M=64, N=4, SKIP=8):**
```
offset' = m * (4 + 8) * 4 + n * 4 = m * 48 + n * 4
bank'(m, n) = (m * 12 + n) % 32

Thread 0 (m=0, n=0):  bank = 0
Thread 8 (m=1, n=0):  bank = 12
Thread 16(m=2, n=0):  bank = 24
Thread 24(m=3, n=0):  bank = (36) % 32 = 4
Thread 32(m=4, n=0):  bank = (48) % 32 = 16
Thread 40(m=5, n=0):  bank = (60) % 32 = 28
Thread 48(m=6, n=0):  bank = (72) % 32 = 8
Thread 56(m=7, n=0):  bank = (84) % 32 = 20

→ No conflicts within a warp! ✓
```

#### Pattern 1b: Row-Based XOR

**Transformation:**
```
offset'(m, n) = (m XOR ROW_MASK) * N * 4 + n * 4

ROW_MASK is typically chosen as power-of-2 submask of N.
```

**Effectiveness:** Better when N is large and contains high-order bits.

**Formula:**
```
If N >= 32:
  ROW_MASK = 8  or  16  (permute bits without losing uniqueness)
If N < 32:
  ROW_MASK = 0  (identity; XOR doesn't help)
```

### Recommended Compiler Strategy (Case 1)

```
Input: M (varying), N (constant), element_size = 4

Step 1: Classify N
  if N >= 32:
    Use identity (standard stride) → bank conflicts unlikely
    return offset = m * N * 4 + n * 4

  if N in [2, 4, 8, 16]:
    Use row-skew padding
    SKIP = lookup_table[N]  // {2:8, 4:8, 8:1, 16:1}
    return offset = m * (N + SKIP) * 4 + n * 4

  if N is odd or N = 1, 3, 5, ...:
    Use row-skew with large SKIP
    SKIP = 16
    return offset = m * (N + SKIP) * 4 + n * 4

Step 2: Validate no out-of-bounds
  smem_size_needed = M * (N + SKIP) * 4
  if smem_size_needed > 96KB:
    fallback to identity (accept conflicts)
  else:
    use swizzled layout
```

## Case 2: M Constant, N Varying (Column-Wise Conflict)

### Physical Interpretation

```
Thread layout:        Memory access pattern (N-indexed variation):
┌─┬─┬─┬─┐            Column 0: [T0   T4   T8   T12]  ← All threads same row
│0│1│2│3│            Column 1: [T1   T5   T9   T13]  ← Same row, next col
├─┼─┼─┼─┤            Column 2: [T2   T6   T10  T14]  ← ...
│4│5│6│7│
├─┼─┼─┼─┤
│8│9│10│11
└─┴─┴─┴─┘
  (warp, row-major)
```

**Key Insight:** All threads in a warp access rows, but from different columns.

### Bank Assignment Analysis

**Without optimization (stride = N):**
```
offset(m, n) = m * N * 4 + n * 4
bank(m, n)   = (m * N + n) % 32

Example: M=4, N=64, thread t in [0, 32) accesses A[t/32][t%32]
  Thread 0:  bank = (0 * 64 + 0) % 32 = 0
  Thread 1:  bank = (0 * 64 + 1) % 32 = 1
  ...
  Thread 31: bank = (0 * 64 + 31) % 32 = 31
  → Within a warp, all 32 threads hit all 32 banks once → Conflict-free!

But if accessing same row with N > 32:
  Thread 32: bank = (1 * 64 + 0) % 32 = (64) % 32 = 0    ← collision with thread 0!
```

### Optimal Swizzle Patterns

#### Pattern 2a: Column-Based Transpose

**Transformation:**
```
Standard layout (row-major):
  offset(m, n) = m * N * 4 + n * 4

Transposed layout (column-major):
  offset'(m, n) = n * M * 4 + m * 4
```

**Derivation:**
```
In transposed space:
  bank'(m, n) = (n * M + m) % 32

Now threads varying in n (column index) naturally spread across banks
because n is the high-order multiplier.

Example: M=4, N=64
  offset'(m, n) = n * 4 * 4 + m * 4 = n * 16 + m * 4
  bank'(m, n) = (n * 16 + m * 4) / 4 % 32 = (n * 4 + m) % 32

  Thread 0 (m=0, n=0):  bank = 0
  Thread 1 (m=1, n=0):  bank = 1
  ...
  Thread 31 (m=0, n=31): bank = (31*4) % 32 = (124) % 32 = 28

  Wait, this causes row collisions now. Transpose alone may not help.
```

**Better approach: Column-Skew (after transpose conceptually)**

#### Pattern 2b: Column-Skew Padding (Recommended)

**Transformation:**
```
offset'(m, n) = m * (N + SKIP) * 4 + n * 4

Same formula as Case 1! But semantically different.
```

**Why it works for Case 2:**
```
bank'(m, n) = (m * (N + SKIP) + n) % 32

In Case 2, m is constant across warp, so term m*(N+SKIP) is constant.
Thus: bank' = (const + n) % 32

As n varies from 0 to 31 within warp:
  → banks cycle through 0, 1, 2, ..., 31 → Conflict-free!

Example: M=4, N=64, m=0, SKIP=8
  offset' = 0 * 72 * 4 + n * 4 = n * 4
  bank' = n % 32

  Thread 0 (n=0): bank = 0
  Thread 1 (n=1): bank = 1
  ...
  Thread 31 (n=31): bank = 31
  → No conflicts! ✓
```

#### Pattern 2c: Column-Based XOR

**Transformation:**
```
offset'(m, n) = m * N * 4 + (n XOR COL_MASK) * 4

where COL_MASK permutes bits in the column index.
```

**Use case:** When N is large and contains distinct high-order bits.

### Recommended Compiler Strategy (Case 2)

```
Input: M (constant), N (varying), element_size = 4

Step 1: Determine conflict severity
  If N <= 32:
    No cross-bank conflicts possible (N threads, 32 banks)
    Use identity: offset = m * N * 4 + n * 4
    return

  If N > 32:
    Conflicts occur for (n >= 32) accessing same row as (n < 32)

    Step 2a: Check SMEM capacity for skew
      SKIP = 8  (heuristic)
      if M * (N + SKIP) * 4 <= 96KB:
        Use column-skew: offset = m * (N + SKIP) * 4 + n * 4
      else:
        if N is power-of-2 and N >= 64:
          Use column-XOR: offset = m * N * 4 + (n XOR 8) * 4
        else:
          Use identity (accept conflicts)
```

## Case 3: Both M and N Varying (2D Conflict)

### Physical Interpretation

```
Thread layout (2D block indexing):
┌──┬──┬──┬──┐        Memory access pattern:
│0 │1 │2 │3 │        (m=0,n=0)  (m=0,n=1)  (m=0,n=2)  (m=0,n=3)
├──┼──┼──┼──┤        (m=1,n=0)  (m=1,n=1)  (m=1,n=2)  (m=1,n=3)
│4 │5 │6 │7 │        (m=2,n=0)  (m=2,n=1)  (m=2,n=2)  (m=2,n=3)
├──┼──┼──┼──┤        (m=3,n=0)  (m=3,n=1)  (m=3,n=2)  (m=3,n=3)
│8 │9 │10│11│
├──┼──┼──┼──┤        Thread t maps to: m = t/N, n = t%N (or other schemes)
│12│13│14│15│        Both m and n change across warp.
└──┴──┴──┴──┘
```

**Key Challenge:** Conflicts depend on **interplay of both m and n** variations.

### Bank Assignment Analysis

**Without optimization:**
```
offset(m, n) = m * N * 4 + n * 4
bank(m, n)   = (m * N + n) % 32

Example: M=8, N=8 (64 threads, one block)
  Thread 0:  m=0, n=0 → bank = 0
  Thread 1:  m=0, n=1 → bank = 1
  Thread 8:  m=1, n=0 → bank = 8
  Thread 16: m=2, n=0 → bank = 16
  Thread 24: m=3, n=0 → bank = 24
  → Spread across banks, but pattern depends on gcd(N, 32)

  Thread 32: m=4, n=0 → bank = (4*8) % 32 = 0  ← Collision with thread 0!
```

### Conflict Pattern Characterization

**Collision condition:**
```
bank(m1, n1) = bank(m2, n2)
⟺ (m1*N + n1) ≡ (m2*N + n2) (mod 32)
⟺ (m1 - m2)*N ≡ (n2 - n1) (mod 32)
⟺ Δm * N ≡ -Δn (mod 32)
```

**Collision groups:**
- If gcd(N, 32) = d, then conflicts occur in patterns repeating every (32/d) rows.
- Within conflict group, threads differing by (Δm, Δn) collide if: Δm * N + Δn ≡ 0 (mod 32).

### Optimal Swizzle Patterns

#### Pattern 3a: Multi-D XOR (2D XOR, Recommended)

**Transformation:**
```
offset'(m, n) = (m XOR M_MASK) * N * 4 + (n XOR N_MASK) * 4

M_MASK, N_MASK chosen to decorrelate both dimensions.
```

**Design principle:**
```
Standard form:
  offset = m * N * 4 + n * 4
  bank = (m * N + n) % 32

With 2D XOR:
  offset' = (m XOR M_MASK) * N * 4 + (n XOR N_MASK) * 4
  bank' = ((m XOR M_MASK) * N + (n XOR N_MASK)) % 32

Goal: Choose M_MASK, N_MASK s.t. for all (m1, n1), (m2, n2) with
  (m1, n1) ≠ (m2, n2) and both in warp access pattern,
  bank'(m1, n1) ≠ bank'(m2, n2)
```

**Heuristic Selection:**
```
Case 3a.1: N is power-of-2, M is power-of-2
  Common case: M=8, N=8 (64-thread block), M=16, N=16 (256-thread block)

  Strategy:
    1. Identify high-order bits of N that matter:
       For N=8:  bits [2:0] are used (values 0-7)
       For N=16: bits [3:0] are used (values 0-15)

    2. Choose M_MASK to XOR with row index:
       M_MASK = high_bit_of_N  (e.g., if N=8, M_MASK=4; if N=16, M_MASK=8)

    3. Choose N_MASK to XOR with column:
       N_MASK = 0 (no XOR needed for column, already unique within warp)

  Example: M=8, N=8, M_MASK=4, N_MASK=0
    Thread 0:  m=0, n=0 → offset' = (0^4)*8 + 0 = 32, bank = 0
    Thread 8:  m=1, n=0 → offset' = (1^4)*8 + 0 = 40, bank = 5
    Thread 16: m=2, n=0 → offset' = (2^4)*8 + 0 = 48, bank = 0
    Thread 32: m=4, n=0 → offset' = (4^4)*8 + 0 = 0,  bank = 0  ← Collision!

    This doesn't fully work. Need stronger mask.

Case 3a.2: Better heuristic: Rotate M_MASK based on leading bits

  M_MASK = rotate_left(N-1, log2(M))
  or simply: M_MASK = (N >> 1)  (half the row width)

  Example: N=8, M=8 → M_MASK = 4
           N=16, M=16 → M_MASK = 8
           N=32, M=32 → M_MASK = 16
```

#### Pattern 3b: Transpose + Skew (Hybrid)

**Transformation:**
```
offset'(m, n) = n * M * 4 + m * (M + SKIP) * 4

Transpose to column-major, then add row-skew.
```

**Derivation:**
```
After transpose, threads naturally spread across different "rows" of transposed space.
Row-skew further decorrelates remaining collisions.
```

**Formula:**
```
SKIP = 8 (conservative choice)
offset' = n * M * 4 + m * (M + SKIP) * 4
bank' = (n * M + m * (M + SKIP)) / 4 % 32
      = (n * M/4 + m * (M + SKIP)/4) % 32
      (assuming M, SKIP multiples of 4)
```

**When to use:** When M is large (> 32) and gcd(N, 32) small.

#### Pattern 3c: Dimension-Wise Permutation

**Transformation:**
```
// Permute tile coordinates before offset calculation
(m', n') = permutation(m, n)  // E.g., swap, rotate, or apply permutation matrix
offset' = m' * N * 4 + n' * 4
```

**Examples:**
```
Swap: (m', n') = (n, m)
  offset' = n * N * 4 + m * 4
  → Reverses the role of m and n in conflict calculation

Partial rotate: (m', n') = (m XOR (n >> 2), n)
  → XOR row index with high bits of column
```

### Recommended Compiler Strategy (Case 3)

```
Input: M (varying), N (varying), both constant compile-time, element_size = 4
       Thread layout: t ∈ [0, M*N) → (m, n) with m = t/N, n = t%N

Step 1: Check if standard layout suffices
  if N >= 32 or (N & (N-1)) != 0:
    // N is not a power-of-2 or N >= 32
    Potential conflicts exist, proceed to optimization
  else:
    // N < 32 and is power-of-2
    Check if M <= (32 / N):
      if yes: Conflict-free already (warp size = 32 threads)
      if no: Conflicts occur

Step 2: Enumerate candidate patterns
  candidates = []

  // Pattern: 2D XOR
  for M_MASK in [N/2, N, N*2, N/4]:
    for N_MASK in [0, 1, 2, 4, 8]:
      candidates.append(("2D-XOR", M_MASK, N_MASK))

  // Pattern: Transpose + Skew
  for SKIP in [1, 2, 4, 8, 16]:
    candidates.append(("Transpose-Skew", SKIP))

  // Pattern: Row-Skew (Case 1 fallback)
  for SKIP in [1, 4, 8, 16]:
    candidates.append(("Row-Skew", SKIP))

  // Pattern: Column-Skew (Case 2 fallback)
  for SKIP in [1, 4, 8, 16]:
    candidates.append(("Col-Skew", SKIP))

Step 3: Simulate and rank
  For each candidate:
    conflicts = simulate_warp_access(candidate, M, N)
    memory_overhead = calculate_smem_size(candidate, M, N)
    candidates.rank(conflicts, memory_overhead)

  best = candidates[0]

Step 4: Validate capacity and return
  smem_needed = best.smem_size()
  if smem_needed > 96KB:
    Fall back to next-best candidate

  return best
```

## Implementation Algorithm Summary

### Unified Decision Tree

```
┌─ Input: (M, N, varying_dims) ───────────────────────┐
│                                                       │
├─ Case 1: M varies, N constant                       │
│  └─ N < 32? → Row-skew(SKIP)                        │
│  └─ N >= 32? → Identity                             │
│                                                       │
├─ Case 2: M constant, N varies                       │
│  └─ N <= 32? → Identity                             │
│  └─ N > 32? → Column-skew(SKIP) or Column-XOR       │
│                                                       │
├─ Case 3: Both M, N vary                             │
│  └─ Check if power-of-2 and dims reasonable         │
│  └─ 2D XOR (primary)                                │
│  └─ Transpose-Skew (fallback for large M)           │
│  └─ Row/Col-Skew (fallback for SMEM pressure)       │
│                                                       │
└─ Output: Transform function θ ──────────────────────┘
```

### Pseudo-Code for Compiler Integration

```cpp
struct SwizzleConfig {
  enum Pattern { IDENTITY, ROW_SKEW, COL_SKEW,
                 XOR_2D, TRANSPOSE_SKEW, HYBRID };
  Pattern pattern;
  uint32_t skip_rows;  // for skew patterns
  uint32_t m_mask, n_mask;  // for XOR patterns
};

SwizzleConfig select_swizzle(uint32_t M, uint32_t N,
                             VariabilityMask varying) {

  // Case 1: Only M varies
  if (varying == VARY_M_ONLY) {
    if (N < 32)
      return {ROW_SKEW, .skip_rows = lookup_skip[N]};
    else
      return {IDENTITY};
  }

  // Case 2: Only N varies
  if (varying == VARY_N_ONLY) {
    if (N <= 32)
      return {IDENTITY};
    else if (has_smem_capacity(M, N, 8))
      return {COL_SKEW, .skip_rows = 8};
    else
      return {IDENTITY};  // Accept conflicts
  }

  // Case 3: Both vary
  if (varying == VARY_BOTH) {
    // Try 2D XOR first
    uint32_t m_mask = (N >= 8) ? (N / 2) : 4;
    uint32_t n_mask = 0;
    if (is_collision_free(M, N, m_mask, n_mask))
      return {XOR_2D, .m_mask = m_mask, .n_mask = n_mask};

    // Fallback: Transpose + Skew
    if (has_smem_capacity(M, N, 8))
      return {TRANSPOSE_SKEW, .skip_rows = 8};

    // Last resort
    return {IDENTITY};
  }

  return {IDENTITY};
}
```

## Validation Framework

### Conflict Detection Algorithm

```python
def check_warp_conflicts(M, N, swizzle_config, warp_size=32):
    """
    Simulate all warp accesses and detect bank conflicts.
    Returns: (num_conflicts, conflict_pairs)
    """
    banks = [[] for _ in range(32)]  # bank[i] = list of threads accessing bank i

    for thread_id in range(warp_size):
        m = thread_id // N if thread_id < M * N else continue
        n = thread_id % N

        offset = apply_swizzle(m, n, swizzle_config)
        bank = (offset // 4) % 32

        banks[bank].append((thread_id, m, n))

    conflicts = sum(len(banks[b]) - 1 for b in range(32) if len(banks[b]) > 1)
    return conflicts, banks

# Test Case 3 with 2D XOR
M, N = 8, 8
config = SwizzleConfig(pattern=XOR_2D, m_mask=4, n_mask=0)
conflicts, banks = check_warp_conflicts(M, N, config)
print(f"Conflicts: {conflicts}/64")  # Expected: 0 or minimal
```

| **1: M varies** | Row-skew | offset = m·(N+SKIP)·4 + n·4 | ~8–16 KB | O(log N) | → 0 |

## Key Takeaways

1. **Case 1 (M varies):** Row-skew is the primary tool. Choose SKIP to decorrelate m·N mod 32.
2. **Case 2 (N varies):** Column-skew uses the same mechanism as Case 1 but exploits constant m. For large N, consider transpose conceptually.
3. **Case 3 (Both vary):** This is the richest optimization space. 2D XOR offers the most control; transpose+skew is a practical fallback balancing SMEM and performance.
4. **Compile-time analysis:** Since M, N are constants, all swizzle costs are static. Enumerate candidates once during compilation.
5. **Validator:** Always simulate warp-level access patterns to confirm conflict-freedom before committing to a swizzle choice.

# SMEM Fallback Strategy: Binary Choice

## Overview

When a tensor configuration doesn't match the three optimal cases, apply a **single, simple fallback decision**:

1. **Try Row-Skew with SKIP=8** if all constraints are met
2. **Otherwise, use Identity** (no optimization)

This binary approach is production-safe: row-skew has clear, checkable constraints; identity is the ultimate safe fallback.

---

## Option 1: Row-Skew with SKIP=8

### Constraints (ALL Must Be True)

**Constraint 1: Both M and N must be power-of-2**
- Valid: 8×16, 16×32, 32×32, 64×64, 128×256
- Invalid: 96×64, 48×32, 32×48, 16×24

Reason: Bijection proof and conflict analysis assume power-of-2 strides.

**Constraint 2: At least one dimension must be an induction variable**
- Valid: M varies, or N varies, or both vary
- Invalid: Both M and N constant (no bank conflicts; no swizzle needed)

Reason: If neither dimension changes, all threads access the same offset; no conflicts possible.

**Constraint 3: SMEM budget must accommodate padding**
- Padding cost: `8 * M * 4 bytes` (SKIP=8, 4 bytes/element)
- Example: M=256 → 8×256×4 = 8,192 bytes overhead
- Constraint: Overhead must be ≤ available SMEM budget

Reason: Row-skew adds `SKIP * M` elements to the allocation.

**Constraint 4: Warp size = 32 threads**
- This is standard for NVIDIA; no action needed in practice

### When Constraints Are Met: Apply Row-Skew

**Memory allocation:**
```c
// Logical shape: M × N
// Physical allocation: M × (N + SKIP)
int skewed_N = N + 8;              // SKIP = 8
float tile[M][skewed_N];           // Size: M * skewed_N * 4 bytes
```

**Access formula:**
```c
float access_element(int m, int n) {
    return tile[m][n];  // Use natural 2D indexing; no special offset math needed
}
```

Or equivalently in 1D:
```c
int skewed_N = N + 8;
int offset = m * skewed_N + n;     // in element units
float value = tile_flat[offset];
```

**Why it works:**
- Natural stride: `(m * (N + 8) + n) * 4 bytes = (m * (N + 8) + n) * 4`
- Bank ID: `((m * (N + 8) + n) * 4) / 4 % 32 = (m * (N + 8) + n) % 32`
- The `+8` term (SKIP) decorrelates row-to-row offsets, spreading threads across banks
- Bijection is preserved: mapping is still one-to-one from logical (m, n) to physical address

### Examples

**Example 1: M varies (1D problem), N constant**

Configuration:
- Shape: 128 × 64
- M = 128 (induction variable: thread_id / 64)
- N = 64 (constant: thread_id % 64)

Constraint check:
- Constraint 1: M=128=2^7 ✓, N=64=2^6 ✓
- Constraint 2: M varies ✓
- Constraint 3: Overhead = 8×128×4 = 4,096 bytes (typically acceptable) ✓

**Decision: Apply row-skew SKIP=8**

Allocation:
```c
float tile[128][72];  // 128 rows, 64+8=72 columns
```

Bank occupancy for thread_id 0..31 (accessing row 0):
```
Thread  | m | n | offset | byte_offset | bank
--------|---|---|--------|-------------|------
0       | 0 | 0 | 0      | 0           | 0
1       | 0 | 1 | 1      | 4           | 1
2       | 0 | 2 | 2      | 8           | 2
...
31      | 0 |31 | 31     | 124         | 31
```
All 32 threads hit different banks → **no conflicts in this warp**.

Bank occupancy for thread_id 32..63 (accessing row 1):
```
Thread  | m | n | offset | byte_offset | bank
--------|---|---|--------|-------------|------
32      | 1 | 0 | 72     | 288         | 8
33      | 1 | 1 | 73     | 292         | 9
...
63      | 1 |31 | 103    | 412         | 31
```
All threads in warp 1 hit different banks (offset by 8) → **no conflicts**.

**Example 2: Both M and N constant**

Configuration:
- Shape: 32 × 32
- M = 32 (constant)
- N = 32 (constant)

Constraint check:
- Constraint 2: Neither dimension varies ✗

**Decision: Use identity** (no swizzle; no conflicts possible since all threads access same (m, n) pair).

---

**Example 3: M not power-of-2**

Configuration:
- Shape: 96 × 64
- M = 96 (not power-of-2)
- N = 64 (power-of-2)
- Both vary (M = thread_id / 64, N = thread_id % 64)

Constraint check:
- Constraint 1: M=96 is NOT power-of-2 ✗

**Decision: Use identity** (cannot guarantee bijection for non-power-of-2).

---

**Example 4: M varies, N varies (both power-of-2)**

Configuration:
- Shape: 64 × 64
- M = 64 (induction variable: thread_id / 32)
- N = 64 (induction variable: thread_id % 32, or thread_id % 64 depending on layout)
- Both vary

Constraint check:
- Constraint 1: M=64=2^6 ✓, N=64=2^6 ✓
- Constraint 2: Both vary ✓
- Constraint 3: Overhead = 8×64×4 = 2,048 bytes ✓

**Decision: Apply row-skew SKIP=8**

Allocation:
```c
float tile[64][72];  // 64 rows, 64+8=72 columns
```

Note: Row-skew handles M variation well. N variation is also covered (conflicts spread across columns), though not with maximal 2D optimization. **This is "trying your best" with a simple, universal fallback.**

## Option 2: Identity (Default Fallback)

### When to Use

Apply identity when **any constraint for row-skew is NOT met**:
- Non-power-of-2 M or N
- Neither dimension is an induction variable (no conflicts possible)
- SMEM budget too tight for padding
- Any doubt about correctness

### Implementation

```c
// No transformation; use natural layout
int offset = m * N + n;  // in element units
float value = tile[m][n];
```

### Cost

- Zero instruction overhead
- Zero SMEM overhead
- Correctness: 100% guaranteed
- Conflicts: Not optimized (but correctness is paramount)

## Compiler Decision Logic

```python
def select_fallback(M, N, induction_dims, smem_budget_bytes):
    """
    Binary fallback selection.

    Args:
        M, N: tile dimensions (compile-time constants)
        induction_dims: set of which dimensions have induction variables
        smem_budget_bytes: available SMEM capacity

    Returns:
        ('ROW_SKEW_8', config) or ('IDENTITY', {})
    """

    # Check all constraints for row-skew SKIP=8
    is_power_of_2_M = (M & (M - 1)) == 0  # M is 2^k
    is_power_of_2_N = (N & (N - 1)) == 0  # N is 2^k
    has_induction_var = len(induction_dims) > 0
    padding_bytes = 8 * M * 4
    has_smem_budget = padding_bytes <= smem_budget_bytes

    if is_power_of_2_M and is_power_of_2_N and has_induction_var and has_smem_budget:
        return ('ROW_SKEW_8', {'skip': 8, 'overhead_bytes': padding_bytes})
    else:
        return ('IDENTITY', {})
```

### C++ Template for Compiler

```cpp
enum FallbackChoice { IDENTITY, ROW_SKEW_8 };

FallbackChoice select_fallback(uint32_t M, uint32_t N,
                               bool m_varies, bool n_varies,
                               uint32_t smem_budget_bytes) {
    // Constraint 1: Both power-of-2
    bool is_pow2_M = (M & (M - 1)) == 0;
    bool is_pow2_N = (N & (N - 1)) == 0;

    // Constraint 2: At least one induction variable
    bool has_induction = m_varies || n_varies;

    // Constraint 3: SMEM budget
    uint32_t padding_bytes = 8 * M * 4;  // SKIP=8, 4 bytes/element
    bool has_budget = padding_bytes <= smem_budget_bytes;

    if (is_pow2_M && is_pow2_N && has_induction && has_budget) {
        return ROW_SKEW_8;
    } else {
        return IDENTITY;
    }
}
```
