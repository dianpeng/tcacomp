# Next Generational IR Representation

# Discussion of existed 0.0.0 compiler

- What was inside of version 1.0
  - 1) Sea-of-nodes style IR
    - Simplified CSE with loop fusion to be value numbering dedup
    - LICM done via scheduling directly
    - Frontend syntax generates nearly zero control flow dependency
      - There is one caveats for out of bound logic representation
    - Sea-of-nodes is good for code that does not have control flow dependency
    - We only keep 2 types of dependencies
  - 2) A relative simple auto paralllization schema
    - We perform auto parallization on loop nests directly
      - Or each axis of iteration space polytope
    - Simple and intuitive
      - A matmul will have 3 axis iteration space polytope
      - We need to assign parallisation assignment for each axis
        - 1) Each axis CAN ONLY BE assigned with a specific type of parallisation
        - 2) Each axis is forced to be tiled
          - ie 3 aixs iteration space is automatically tiled into 6 nested loops
        - 3) A simple solver via brutle force
          - Based on a simple objective function and constraints
            - SM utilization + SMEM constraints
        - 4) Very easy to insert SMEM cache
  - 3) Mechanical lowering process + Runtime utility
    - lowering process is almost mechanically
      - We do not even have a classical CFG representation since we do not need it
      - Lowering of Sea-of-nodes into **AST style CFG representation**
        - Structural representation is our needs
    - Runtime object hides most of the complexity with specializtion
      - Compiler is able to instruct runtime for specialization
        - Ie warp based reduce specialization

- What's the problem ?
  - [1] The per dimensional fixed parallisation schema will ONLY allow 1D tiling
    - For example:
      - we can only assign a full WARP to a specific dimension
      - but typical cuda optimization happens on WARP per **TILE**, a TILE is at least a 2D data
      - this makes tensorization impossible to implement
      - also no way to do batched cache for output, since each time will ONLY generate a single element
  - [2] We do not have any control flow modeling, but it has an issue
    - We need control flow modeling to at least show **out of bounds guard** in IR
    - For us, the PHI is not needed, this is true
      - It is impossible for user to write branched value
      - Ternary is expressed as simple select builtin function
  - [3] Cannot optimize to a **very performant compiler**
    - Typical CUDA optimization
      - 0) auto parallisation
      - 1) operand caching
      - 2) 1D tiling
      - 3) ND tiling
      - 4) warp tiling
      - 5) tensorization
      - 6) vectorization (single thread)
      - 7) fuse operation
      - 8) tensorization
      - 9) GMEM coalesence
      - 10) bank conflicts avoidance
      - 11) software pipeline
      - 12) warp specialization
      - 13) mega kernel, somehow correlated to wrap specialization

    - What we can do
      - 0, 1, 2, 6, 9, 10
        - 0: yes we do, dimension based parallisation
        - 1: yes, cache insertion automatically
        - 2: yes, similar to cache insertion, TBI
        - 6: yes, loop unrolling + ILP, TBI
        - 9: yes, we can perform mutation of axis to allow GMEM
          - similar to triton
            - slope analysis against subscript expression
            - ranking per unit bump per axis of loaded memory
              - notes, it means we must have assumption of how GMEM's tensor dimension looks like
            - and swap the slowest bump per unit for last dimension
              - which has more chance to hit 128bytes simutanesouly
            - within WARP
        - 10: yes, this is the cheapst, TBI
          - analysis the SMEM, shape known
          - choose a swizzle bank pattern
          - instruct runtime to use that swizzle bank pattern
          - swizzle bank is part of runtime implementation
      - rest is impossible
  - NOTES:
    - Many optimization is not implemented simply because they are trivial to implement
      - 1) SMEM reuse via RA
      - 2) expression level optimization
        - constant fold
        - algebra reassociation
        - normalization
        - ...
    
- Overview Assessment
  - 1) Sea-of-nodes **is a good fit**
    - It is really good for cuda DSL, since DSL typically have following characteristics
      - 1) NO side effect function call, side effect is only on memory operation
      - 2) NO control flow
      - 3) Data dependency can be used to represent control flow if really needed
        - For example loop control flow dependency is always explicit, ie via
          - loop induction variable reference
      - 4) Almost all nodes in the graph can be numbered
        - GVN can be extreamly useful
      - 5) Scheduling using sea-of-nodes can simplify many code motion
        - since most code can be moved, not too much control dependency
  - 2) Data immutability
    - We do not allow in place modification at all
    - All memory node is assumed to be aliased
      - Notes subscript is not
    - Which means the loop underlying is always ready to be parallized
    - No need to introduce complicated contraints based loop transform
      - ie polyhedral optimization
    - In place modification can be expressed as an optimization pass in the future
      - ie liveness interval + reuse
      - similar to RA

  - 3) Iteration/loop is the **wrong abstraction** at all
    - This is the biggest mistake
    - Working on loop is wrong, cuda/parallisation is never about the loop
      - We picture parallisation as specialized loop structure
        - ie strided loop for various parallisation scope
      - loop tiling is enforced, hence we pair the assignment of parallisation for inner and outer loop
      - However
        - cuda is not about the loop, it is about structural/heirachy parallisation
        - loop is only a final materialization for the parallisation
        - plus cuda code can be totally loop free, with correct launcher setup
    - We must have a better abstraction, instead of loop
      - Loop is the materialization mechanism for parallisation
        - ie purely code, not the abstract entity

  - 4) The abstraction for optimization must enable us to implement optimization pass in foreseenable future
    - (1) tensorization
    - (2) vectorization
    - (3) warp/warp group specialization
    - (4) software pipeline
    - (5) mega kernel
    - The above advanced optimization requires the organization of the code as
      - 1) CTA centric, ie CTA as worker
      - 2) Dispatching of CTA to be opaque, ie hidden in runtime
    - Overall the optimization must be
      - 1) Within CTA, performs local in loop based optimization to bring up CTA level performance
        - Tensoriazation: VERY IMPORTANT
        - Memory optimization
        - ...
        - Advanced organization
          - Software pipeline
          - Warp specialization
      - 2) Cross CTA scheduling
        - (1) Default CTA method
          - ie a loop to dispatch multiple CTA level works on given tile
          - simplest runtime dispatcher
        - (2) Fancier dispatcher
          - ie megakernel, event based method

# Goal

- This is the goal that our radically new compiler backend design needs to achieve

  - (1) Enablement of advance optimization for CUDA
    - [1] tensorization
    - [2] warp specialization
    - [3] software pipeline
    - [4] mega kernel (POTNETIALLY)

  - (2) Potential support for **multiple GPU vendors**
    - NOTES: we are still preparing for CUDA for this design, but leave the possible for other GPUs

    - IR to be in different layered
    - 3 Layer IR system
      - (1) CIR(sea-of-nodes): common ir
        - Simplification
          - map map inline
        - Expression Optimization
        - GVN
        - DCE
        - Type Inference
      - (2) BIR(sea-of-nodes): backend ir
        - tiling strategy
        - auto parallisation
        - memory optimization
          - GMEM coalescense
          - SMEM bank conflicts avoidance
          - operands caching
        - opreation lower
        - specialized optiomization
          - tensorization
          - software pipeline
          - vectorization via loop unroll
        - lower
      - (3) LIR(CFG style): low ir
        - ready for code generation
        - notes this is also kind of complicated
          - For now, we can assume we are targeting at
            - 1) CUDA/C++ for NV
            - 2) HIP for AMD
            - 3) DPC++ for Intel
          - Better just lower them into ast style CFG since the code generation is really C++ generation
  - (3) Generate performance competitive GPU code
    - For example on CUDA backend, which is our target one, we should be within 20% of cutelass
