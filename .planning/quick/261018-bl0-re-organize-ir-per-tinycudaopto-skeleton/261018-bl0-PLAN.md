<objective>
Re-organize tcacomp's two-level IR (`internal/ir`, landed by quick-261017-vdj) to match the
tinycudaopto skeleton (`/home/ps/Workspace/cuda/project/tinycudaopto/internal/ir/` — the
comments there are the spec) across the user-mandated requirements:

- **R1 — sea-of-nodes dependency model** (already holds; preserve): data flow via operand
  Inputs, effect order via ImpactBy edges. Input + ImpactBy together define a valid PARTIAL
  ORDER (poset) of possible placements — enough to restore CFG order any way desired.
- **R2 — one end node**: the whole program is a def←use chain graph (edges point at inputs).
  The graph keeps ONE end/return node carrying ALL kernel-observable effects: the return
  value(s) AND every memory node passed in via kernel parameters (they are part of the
  Environment). Stores are NOT effect roots; they chain into the memory param's effect
  chain, and the end node references each param's final chain head via ImpactBy.
- **R3 — trivial two-root-set DCE**: mark reachable from (a) the return value (the end
  node) and (b) memory nodes passed in as parameters → alive; erase everything else, even
  effectful-looking nodes. In-program memory (SMEM/FRAG caches) is observable only inside
  the kernel and is NOT a DCE root.
- **R4 — layered re-organization**: (a) every node category gets its own `node_xxx.go`
  file; (b) the node suite matches tinycudaopto's HIR set with HIR/LIR separation, pipe
  nodes absent (tcacomp has none — grep-verify only); (c) concepts split into dedicated
  files (nodes by category, walk, verify, dce, schedule/default-materialize, effect/env,
  poset APIs, ssa handles); (d) LIR: LoadTile/StoreTile REMOVED, replaced by
  MemLoadSMem/MemStoreSMem/MemNewSMem plus FragLoad/FragStore/FragNew (tinycudaopto names
  the SMem trio in memory.go; it has no explicit Frag node names, so use
  FragLoad/FragStore/FragNew); HIR MemLoad/MemStore/MemNew are the GMEM family; the generic
  Load/Store is GONE entirely; (e) a DEDICATED file (`catalog.go`) lists all known IR nodes
  categorized HIR/LIR.
- **R5 — scheduler is an optimization PASS, not an IR primitive**: internal/ir keeps the
  sea-of-nodes + Input/ImpactBy poset, the CFG/BB/Statement structures, poset query APIs,
  and only a minimal correctness-preserving default `Materialize` (needed by tests/goldens
  and simple builds). The real scheduler — stable topological placement onto the CFG
  according to the poset, WITH LICM (it tries to HOIST loop-invariant nodes during
  scheduling) — lives in the pass pipeline as `pass.Scheduler` (internal/pass), one of the
  optimization passes before codegen.
- **R6 — golden policy flip**: unlike 261017-vdj, goldens WILL legitimately change
  (Kind names change: Store→MemStore, tile kinds gone). Regenerating goldens is expected
  and allowed; the correctness gate is `go test ./...` green with goldens regenerated
  DELIBERATELY (reviewed diff), then byte-stable for the rest of the task.
