## Narrative Findings (AI reviewer)

### HI-01: R3 element bracket is placed in the OUTERMOST element loop — structurally wrong for ≥2 between dims

**File:** `internal/opt/finallower/reducer.go:302-336, 374-381, 429-440`

**Issue:** `buildElementLoop` builds the fresh element chain innermost-first (i = len−1 downto 0); each newer block wraps the previous (`blk.InsertItemAt(0, …Block: innerBlk)`), so after the construction loop the variable `innerBlk` holds the block of `betweenBlks[0]` — the **outermost** element loop. Init (line 333), X's block (line 375), Combine (line 380), and the moved epilogue consumers (line 438) are all inserted into it, while the comment (line 330) and the ruling (doc/tca.md §5.10: "Init is the first statement of the element loop … Combine sits immediately after @r_o … Combine runs **once per output element**") require the **innermost** loop.

At `len(betweenBlks) == 1` outermost == innermost and the shape is correct (this is the golden and `TestReducerBracketPlacement`). At `len ≥ 2` the produced structure is `[elem(e0): [Init, elem(e1): ⟨empty⟩, X[home[…Reduce]], Combine, consumers…]]`:

- Combine fires once per `e0` element while the walk spans all `e1` elements — one bracket per outer element instead of per output element `(e0, e1)`; the Combine value folds `(e1 × reduced)` rather than the per-element reduction.
- The rebuilt walk/consumer coordinates reference `freshIVs[1..]`, dimvars whose loops close before X runs — the emitter fails at `expr.go:27-31` ("dimvar has no enclosing loop in scope"). The moved store's `e1` coordinate is exactly such a reference.
- `elemDepth` (line 328: `scopeDepth(parentBlk) + len(betweenBlks)`) and `SetSched(elemDepth, innerBlk)` stamp the innermost depth against the outermost block — inconsistent linkage.

**Failure scenario:** reduce over the last axis of a rank-3 tensor `tensor<f32, M, K, N>` with `M` and `K` both tiled T>1 (the between set is then `[m.inside, k.inside]`; both are T>1 whenever the uniform tile sweep picks t>1 for the window). doc/syntax.md's own pipeline example is exactly `(m, k, n) -> reduce -> (m, k) -> reduce -> (m)`. No test in `finallower_test.go` constructs more than one between dim, so this is invisible to the suite.

**Fix:** track the actually-innermost block (the first `blk` built, i.e. capture it when `i == len(betweenBlks)-1`) and place Init/X/Combine/consumers there; stamp with that block's depth. Alternatively, fail closed now (`len(betweenBlks) > 1` → named error "multi-element-dim reduce brackets not yet implemented") so the shape is a documented refusal instead of corrupted IR, and add a two-between-dims fixture test.

### HI-02: T==1 flat bracket leaves Combine's local inside the wrapping element loop — the epilogue store reads it out of C++ scope

**File:** `internal/opt/finallower/reducer.go:228-246`

**Issue:** The T==1 path inserts Init before X and Combine after X **in X's parental block**. When the reduce has a T==1 non-reduced dim, X's parental block is that dim's single (between) loop block — e.g. nest `[m.single[ X(k.between)[ home[…] ] ] ]` puts `auto vN = reducer.Combine();` inside the m-loop. The consuming store — the standard reduce tail the scheduler lands in the **nest epilogue** (confirmed by the redFx fixture comment, `finallower_test.go:582-583`) — sits in the cluster Group **after** the nest. The emitter materializes the Combine at its statement position (`runtime.go:215-223`) and the store re-reads that local (`statements.go:137`): the generated C++ references a variable declared inside a loop that has already closed → nvcc compile error. Unlike HI-01 this cannot be caught by any IR-level check; it only fails at C++ compilation.

**Failure scenario:** any reduce kernel whose non-reduced element dim resolves at tile 1. This is not exotic: the searcher always enumerates t=1, and when no site promotes (reuse < 2, e.g. a reduce whose lhs is read once per element) every candidate scores 0 traffic and the **first** maximum — the t=1 vector — wins (`search.go:128`). No finallower test exercises a T==1 reduce with a store consumer.

**Fix:** in the T==1 branch, apply the same consumer move as `buildElementLoop`: relocate epilogue items whose operand closure reaches `combineCall` to immediately after Combine inside `parentBlk` (rebuilding their coordinates onto the single-loop IV), or place Init/Combine at the cluster-Group level when the bracket's parent is not the Group.

### HI-03: No gate enforces `tile ≤ coupledThreads` — the C1 flat-init walk's single-ownership silently becomes double-ownership (race) for legal Params

**File:** `internal/opt/tiling/lower_rewrite.go:430-464` (the coupled walk), `internal/opt/tiling/record.go:408-445` (Validate), `internal/opt/tiling/verify.go`

**Issue:** The C1 walk is `init = thread_map.index()` (flat rank), `step = coupledThreads`, `bound = tileMax` (comment at lower_rewrite.go:441-442 states the contract: "single-owner exact **while tile <= coupled**"). With `MaxThreadsPerCTA = 512, WarpPortion auto (4)` → `coupledThreads = 256`. Every thread `t` walks rows `{t, t+256, …} ∩ tile`, so any row `r ≥ 256` inside a tile `tileMax > 256` is walked by **two** threads (`t = r` and `t = r−256`). In a matmul-shaped kernel both threads then execute `out_v.Set(v17, v12, …)` for the same address — a write-write race that violates the project's core invariant (structural stores, one owner per address) and would be flagged by racecheck.

Nothing enforces the contract: `Params.Validate` only checks tiles ≥ 1; `evalSchedule` gates only the F2 warp-portion floor; tiling-verify re-checks LoC/TileSize ≥ 1 and the F2 floor, never `tile ≤ coupled`. Defaults are safe only by coincidence (`TileSizes` max 256 == coupled 256).

**Failure scenario:** a caller (the Params surface is documented as externally provided, `record.go:299-301`) passes `TileSizes: {512}` — valid per Validate — and gets a racy kernel for any CTA-dim kernel whose body stores through the coupled walk.

**Fix:** gate in `evalSchedule` (skip or error on vectors whose CTA dim's effective tile exceeds `ctx.coupledThreads`) and mirror it in tiling-verify's per-iter feasibility sweep, with a named reason. Document the constraint beside the F2 floor.

### MD-01: Chained reduce-after-reduce breaks the @r derivation after the first Reduce is lowered

**File:** `internal/opt/finallower/reducer.go:74-84` (allocation-order loop) + `215` (RAUW) + `582-606` (`deriveReducedDim`)

**Issue:** `lowerReducers` processes Reduces in allocation order. For a chain `Reduce₂.op0 = Reduce₁`, lowering `Reduce₁` first RAUWs it onto its Combine call, so when `Reduce₂` is reached, `redOp0(red₂)` is a `RuntimeCallMethod`, the chase in `deriveReducedDim` sees neither a Reduce nor a Map, and the pass hard-errors ("no producing Map/As chain derivable"). The Reduce→Reduce recursion in the chase can only ever fire on chains that have not yet been lowered — i.e. never, given pipeline order.

**Failure scenario:** doc/syntax.md's canonical multi-dim reduction `(m, k, n) -> reduce -> (m, k) -> reduce -> (m)` (once the frontend exists, or via builder-level IR today). Loud failure, not silent — but a documented shape the compiler cannot build.

**Fix:** two-phase: derive and cache every Reduce's (dim, producingMap, piped) before lowering any of them, or let the chase follow a Combine call back to its reducer's recorded piped value.

### MD-02: f64/i64/u64 reductions rejected — byte-size tables have no row for 8-byte scalars

**File:** `internal/opt/finallower/reducer.go:564-575` (`elemBytes`), `internal/cg/cxx/naming.go:48-63` (`elemByteSize`)

**Issue:** Both size tables stop at 4-byte elements. A reduce whose element type is `f64`/`i64`/`u64` — legal input per doc/syntax.md ("input element type, initializer type … must all be the same scalar type T"; `tensor<f64, …>` is in the type grammar) — fails at final-lower with "no pinned byte size for element type". Fail-closed, so not a correctness bug, but an undocumented functional gap: neither doc/rt.md §4.6 nor the syntax doc records the restriction.

**Fix:** add the 8-byte rows (`double`, `int64_t`, `uint64_t`) to both tables, or document the v0 restriction where reducers are specified.

### MD-04: Non-moved consumers of the Combine value are not guarded (Returns, cross-cluster users)

**File:** `internal/opt/finallower/reducer.go:396-407` (`qualifies` excludes `KindReturn`; the scan covers only the owning LNT's cluster group)

**Issue:** After the element-loop move, any surviving AST item whose operand closure reaches `combineCall` but was not moved (a `Return` consuming the reduced value, or a consumer living in another LNT's cluster) references a node defined inside the element loop — lexically out of scope. The failure then surfaces late, as an emitter error or a bad dump, rather than as a named final-lower diagnostic. Unreachable with today's store-only kernels, but the exclusion is silent rather than checked.

**Fix:** after the move, fail closed if any non-moved live item's closure contains a Combine call ("consumer of the reduced value cannot be placed outside the element bracket").

### MD-05: cg.Options vs tiling-Params thread-count consistency is only checked when a reducer exists

**File:** `internal/cg/cxx/runtime.go:136-155` (`stagingCount` cross-check); `internal/cg/cxx/emit.go:160` (`__launch_bounds__`, launch dims from `opts`)

**Issue:** The coupled walk's step (256), the mirror-gate extents, and the staging row are all baked from tiling `Params`, while `blockDim.x` in the generated launcher comes from `cg.Options`. `stagingCount` catches a disagreement, but only for kernels with a warp/global reducer; a matmul-shaped kernel with mismatched Options/Params compiles to a kernel whose ThreadMapping decomposes a different thread space than the compiler assumed — silent coverage/ownership corruption, no diagnostic.

**Fix:** assert `prov.MaxThreadsPerCTA == opts.MaxThreadsPerCTA` (and `MaxCTA`) at `Emit` entry, fail-closed for every kernel.

### LO-01: `rebuildWithSubs` silently discards substitutions for non-clonable interior kinds

**File:** `internal/opt/finallower/reducer.go:694-695`

**Issue:** When an operand changed but the node kind is not in the clone switch, the function returns the **original** node with unbuilt operands — the substitution is dropped without an error. The tiling twin (`cloneWithOperands`, lower_cache.go:694-711) documents the same default as a leaf carve-out, but here interior nodes (any future coordinate-carrier kind) would be silently mis-rebuilt. Contradicts the pass's fail-closed discipline; today's coordinate kinds (BinOp/Call/DimVar/GetAttr roots) happen to be covered.

**Fix:** fail closed on `changed && !clonable` (a named error), matching the pass's own philosophy.
