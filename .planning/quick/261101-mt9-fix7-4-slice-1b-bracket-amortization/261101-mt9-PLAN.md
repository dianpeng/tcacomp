## The §4 chunk-fold DECISION (made here, with rationale)

DECISION: codegen explicit accumulator — a chunk-wide Frag block spanning X's FULL walk —
with the combiner body inlined per element. NO runtime SeqReducer chunk-fold entry. NO
per-round partials.

Rationale:
1. The per-chunk accumulator is inherently a chunk-wide ARRAY (one accumulator per output
   element of the chunk). A runtime SeqReducer holds ONE scalar acc_; expressing the block at
   runtime would require a NEW template-sized block-reducer class — new runtime surface against
   the minimal-runtime doctrine (R1 struck template sizing from the reducer protocol) — and
   codegen would still have to declare/emit the block, so the runtime entry saves nothing.
2. §4's partials concern dissolves under this shape: the block accumulates across ALL of X's
   chunk rounds by construction, so there are NO chunk partials to fold. The runtime fold
   entry (scalar Fold(T partial)) has no work. For the suite (const K=4/8, single round) and
   for dynamic-K shapes alike, the emitted structure is identical — one Init walk, one store
   walk, zero fold machinery.
3. The combiner body is a pure homogeneous scalar expression (LR-8-checked at construction);
   map lambdas are already inlined the same way by Map Lower (RAUW onto the lambda body
   expression, maplower.go). Cloning it over (acc-slot load, piped) reuses the verified
   rebuildWithSubs machinery. Reducer SEMANTICS are unchanged — one-tier per-thread
   accumulation, k-ascending per element, single-owner ungated stores — ceremony count only,
   exactly §4's constraint.
4. Runtime zero-diff: runtime/tca/reducer.h untouched (layernorm/transpose keep their
   SeqReducer — they fail the qualification below — so the class stays load-bearing).

LR-3 amendment note (record it in the code comment too): LR-3's "the compiler emits no
lambda-call node and never reads current_value/init" is amended FOR THIS SHAPE ONLY by fix7
§4's explicit authorization of the codegen-accumulator branch. The amendment is shape-scoped
(amortized one-tier flat bracket); every other reducer shape keeps LR-3.

## Fill-placement-gap verdict: INSEPARABLE — in scope as one restructure

The task brief asks whether the §3.4 fill-placement fix is separable. Investigation verdict:
it is NOT. The fill's gap-closing position IS its current X-scoped derived position ("fill
position = dominated-by-operand-scope LICM, re-derivable after any reshape" — the 2026-10-25
ruling): the fill must stay inside X because its k coordinate iterates with X's IV; it is
per-element only because the element walk encloses X. Closing the gap REQUIRES inverting the
nesting (element walk inside X), which is the bracket amortization reshape. No separate
fill-placement task exists; the schedule pass is untouched; the D-j scope discipline is
preserved (the fill stays in X, reads stay in home inside the element loop inside X — the
assertFillReadsInside epoch contract holds: the fill precedes every read of its buffer within
each X round). If a qualifying kernel strands a fill coordinate, Q3 fails closed for it.

## Qualification (ALL must hold, else fail closed to today's per-element shape — never a guess)

- Q0: the bracket's tiered fills are FRAG-class per-thread sites only; any SMEM-class
  (LoadTileCta, cooperative) site in X disqualifies the kernel (1d territory).
- Q1: construction is KindRuntimeSequentialReducer (one-tier). Warp/Global (multi-tier,
  CTA-collective sync protocol — incl. the whole split-k matmul family) never qualify.
- Q2: the flat-bracket degenerate only — betweenBlocks(xBlk, homeBlk) is EMPTY (X directly
  contains home). The R3 buildElementLoop shape (non-empty between set) keeps today's shape.
- Q3: NO fill item inside X has a window coordinate expression referencing the enclosing
  element walk's IV. (This is what makes the inversion safe: the fill rides at X level. The
  counter-case — layernorm/transpose, whose windows cover the reduced dim and whose fill
  coordinates DO reference the element IV — fails here and keeps today's shape.)
- Q4: exactly ONE uniform sequential element loop directly encloses X's bracket scope (X's
  parental block is its body; the loop above it, if any, is thread-specialized like the
  ThrIterator coupled walk — each trip gets its own bracket, as today). Its body contains
  exactly [Init call, X block, Combine call, the moved consumers] — anything else is a named
  error. (Multi-dim uniform element chunks, e.g. layernorm's two C walks, fail here.)
- Q5: every Combine-value consumer passes the existing moveCombineConsumers gates with its
  coordinates rebuilt onto the fresh store-walk IV: no reduced-dim dimvars, enclosure
  assertions over the store-walk position. Reduce-after-reduce chains (the Combine feeding
  another reduce) disqualify.
